# E2E Run, 2026-09-04 — Four Defects a Green Suite Could Not See

**Status:** findings applied; run in progress at time of writing.
**Book:** `tests/fixtures/sample_book.epub` — 8 chapters, 11,874 words, 67,927 chars.
**Project:** `sample_book-1`. **Model:** `qwen3.8:27b` via Ollama, `num_parallel: 1`.

The suite was green — 613 pytest, 563 unittest, 10 frontend, ruff clean — when
this run started. It died five minutes in, and the three defects found while
recovering it were each worse than the one that stopped it.

---

## 1. The crash: an attribute that never existed

```
AttributeError: 'CharacterAnalyzer' object has no attribute 'config'
  character_analyzer.py:595 in _adjudicate_cast_identity
```

`self.config` was read to decide the cast-approval default. `__init__` never
assigned it and no caller ever passed one, so the first real book to reach
duplicate detection ended the run.

**Why 36 tests missed it.** The fixture built the analyzer with
`object.__new__(CharacterAnalyzer)` and set the attributes by hand — `config`
among them. The test supplied the exact thing production was missing, so the
suite asserted against an object shape that exists nowhere else in the
codebase. Changing the fixture to use the real constructor makes three
*pre-existing* tests fail against the old code; they were always meant to
catch this and simply could not.

> A fixture that constructs its subject by hand is asserting against a model of
> the object, not the object. `object.__new__` in a test is worth treating as a
> defect on sight.

**Also fixed:** the call site was unguarded. Duplicate detection is advisory —
the pipeline made books for months before it existed — but only the Gemini
call had a `try` around it, so a failure in roster construction, config or
alias recovery ended the run. A roster with a duplicate left in beats a dead
book, and it degrades that way now.

## 2. The checkpoint was deleted before the work that could still fail

Pass 1 writes `characters.checkpoint.json` per unit. It was deleted the moment
Pass 1 parsed its registry — with adjudication, augmentation and voice
assignment still ahead, and the caller only persisting `characters.json` after
all of them return.

So any failure in that window discarded the entire discovery pass. The run
died after **unit 9 of 9** and the retry restarted at **unit 1**.

Deleting it after the registry is complete, the next retry resumed at **unit
4**. Discovery is the expensive half of scripting; nothing advisory should be
able to spend it.

## 3. The launcher force-killed whatever held port 8000

```powershell
function Stop-StalePort8000Process {
    Get-NetTCPConnection -LocalPort 8000 | ForEach-Object {
        Stop-Process -Id $_.OwningProcess -Force
    }
}
```

Nothing here checks that the process is stale. It ran at the top of every
supervisor iteration and at launcher start, and Task Scheduler reaches that
code on its own: the task is registered `-RestartCount 3 -RestartInterval 1
minute`, and `restart_dashboard.ps1` can call `schtasks /End`, which Task
Scheduler records as a failure. A phantom relaunch a minute later could kill a
completely healthy dashboard mid-book.

It now probes `/api/health` first:

| Listener state | Action |
| --- | --- |
| Reports `pipeline_running` | Refuse; return `$false` and let the caller back off |
| Healthy and idle | `POST /api/system/shutdown`, wait out the grace period |
| Answers nothing | Force-kill — the case the function was written for |

Verified against the live hazard: with a run in flight the function refused and
the dashboard survived.

## 4. A GPU release stops runs and says nothing

`_release_gpu_resources` interrupts every active project. The pipeline records
that as `"Interrupted by user"` with **no `pause_reason`** — byte-identical to
someone pressing stop in the UI. Two runs paused unexplained during this
session and the logs could not distinguish shutdown, restart, release-gpu and
the UI, all four of which are reachable from the dashboard, Home Assistant,
the desktop shell and two PowerShell helpers.

The release now names the runs it is interrupting, and `/api/system/shutdown`,
`/api/system/restart` and `/api/system/release-gpu` each log the caller's
address and user-agent.

**This is instrumentation, not a diagnosis.** The trigger for the two pauses
was not established. `/api/projects/{id}/stop` was ruled out (it always sets a
`pause_reason`), as were the desktop shell (not running) and the schedule
window (18:41 sits inside 09:00–19:00 Europe/Bucharest). The Task Scheduler
retry above is the leading hypothesis and matches the timing, but it is a
hypothesis.

## Process notes

**The monitor missed the crash.** The watch pipeline ended in `cut -c1-220`,
which does not line-buffer, so every event sat in its buffer while the run
died. The failure was found by polling manually. Filters that end in a
non-flushing stage are silent, and silence reads exactly like "still running".

**Green means the assertions passed, not that the code works.** Every defect
here survived a full green suite. Three of the four are invisible to unit
tests by construction: two live in PowerShell and Task Scheduler
configuration, and the third is an ordering property across a function's whole
body.
